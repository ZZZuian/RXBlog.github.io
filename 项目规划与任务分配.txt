================================================

文档版本：V2.2（参考 XHBlogs UI 与音乐体验后修订）
文档日期：2026-06-29
项目定位：面向多元兴趣群体、鼓励不同主题和平交流的包容型博客社群

一、产品定位与核心原则
======================

1. 产品定位
-----------

本项目不是把多个互相不可见的个人博客放在同一个系统中，而是建设一个“公开社区内容流 + 用户个人博客主页”的博客社群。

平台同时具有两种浏览视角：

  （1）社区视角
      首页统一内容流向所有用户展示社区成员发布的内容；用户可以通过标签发现不同兴趣内容、阅读博文、点赞和评论。

  （2）个人视角
      每位用户拥有独立主页，用于集中展示自己的博文、头像、简介、背景图和背景音乐，并提供访客留言板。

2. 核心原则
-----------

  P1  内容公开：正常发布的博文进入社区公共内容流，不能按当前登录用户隔离。
  P2  权限私有：只有作者本人可以编辑或删除自己的博文；平台管理员可以执行审核和下架。
  P3  互动真实：点赞、评论必须记录互动用户，不能只在浏览器 localStorage 中模拟。
  P4  多元包容：平台只有一个统一社区，不用板块划分群体；追星、Vtuber、音游及其他兴趣通过自由标签表达。
  P5  主页可达：帖子作者昵称可点击，访客能够进入作者个人主页继续浏览和留言。
  P6  设置分层：平台系统设置、后台管理、账号安全设置、个人主页设置必须分开。
  P7  安全优先：文件上传、用户输入、权限验证和后台操作必须经过服务端校验。

3. 本期范围
-----------

  必须实现：
  - 多用户账号注册、登录、退出、修改账号、修改密码
  - 社区首页公开内容流
  - 单一、包容的社区内容流与标签发现
  - 博文标题、正文、多图片、标签
  - 用户间点赞和评论
  - 用户个人主页及其博文列表
  - 头像、背景图、背景音乐、简介设置
  - 个人主页留言板
  - 基础后台管理和内容治理
  - 原有数据迁移与自动化测试

  暂不纳入本期：
  - 私信、关注、粉丝系统
  - 复杂推荐算法
  - 实时聊天、直播功能
  - 付费内容和商业化
  - Markdown 编辑器（可在核心功能稳定后作为增强项评估）


二、用户角色与权限模型
======================

1. 角色定义
-----------

  游客 guest
  - 可浏览社区首页、标签聚合、博文详情和用户主页
  - 不可发帖、点赞、评论或留言

  注册用户 user
  - 拥有游客全部权限
  - 可发帖、点赞、评论、在用户主页留言
  - 可编辑和删除自己的博文
  - 可维护自己的账号安全和个人主页设置

  平台管理员 admin
  - 拥有注册用户权限
  - 可进入后台管理
  - 可管理用户状态、帖子、评论、留言和平台级设置
  - 管理操作必须记录日志

2. 内容权限矩阵
---------------

  功能              游客      注册用户        内容作者        管理员
  -----------------------------------------------------------------
  浏览公开博文      允许      允许            允许            允许
  浏览用户主页      允许      允许            允许            允许
  发布博文          禁止      允许            允许            允许
  点赞/取消点赞     禁止      允许            允许            允许
  发表评论          禁止      允许            允许            允许
  编辑/删除博文     禁止      禁止            允许            允许/下架
  主页留言          禁止      允许            允许            允许
  修改个人资料      禁止      仅本人          仅本人          不代改密码
  后台管理          禁止      禁止            禁止            允许

说明：所谓“用户数据隔离”仅指账号安全、草稿、编辑和删除权限隔离，不代表公开博文互相不可见。


三、产品信息架构与四大基础模块
============================

1. 系统设置
-----------

系统设置仅供管理员使用，管理平台名称、平台简介、默认背景、上传限制、允许的文件类型和社区公告等全局配置。

2. 后台管理
-----------

后台管理提供用户列表、用户封禁/解封、帖子下架/恢复、评论与留言删除、数据统计和管理日志。

3. 登录与账号设置
-----------------

注册和登录使用唯一账号 username，不再使用邮箱。用户可以修改账号和密码。账号安全设置与公开昵称、头像等个人资料严格分离。

4. 日志与博文展示
-----------------

“日志”升级为社区博文。首页展示全站最新公开博文；标签页聚合具有相同兴趣标签的内容；个人主页仅聚合指定作者的博文。三者使用同一份帖子数据，只是查询条件不同。

5. 社区扩展模块
---------------

  - 博文发布与多图片上传
  - 统一社区内容流与标签发现
  - 点赞与评论
  - 用户个人主页
  - 主页背景图与背景音乐
  - 访客留言板


四、关键页面与用户流程
======================

1. 首页 /
---------

  - 显示全站所有状态为 published 的最新博文，而非当前用户自己的博文
  - 支持按发布时间分页
  - 卡片显示标题、摘要、首图、作者、时间、标签、点赞数和评论数
  - 点击作者进入 /user/<user_id>
  - 点击标签进入 /tags/<tag>
  - 点击卡片进入 /post/<post_id>

2. 标签聚合页 /tags/<tag>
--------------------------

平台不划分兴趣板块。用户可自由添加追星、Vtuber、音游、生活、技术等标签，标签页聚合全站具有相同标签的公开博文。

3. 发帖流程 /post/new
---------------------

  登录 → 填写标题和正文 → 添加标签 → 上传图片 → 预览/提交 → 进入详情页。

每篇帖子必须记录 author_id；标题和正文必填；标签和图片可选，图片支持多张。

4. 博文详情 /post/<post_id>
----------------------------

  - 展示正文、图片、作者资料入口和标签
  - 注册用户可点赞/取消点赞、发表评论
  - 作者本人可见编辑和删除按钮
  - 非作者直接调用编辑/删除接口必须返回 403 或 404

5. 用户主页 /user/<user_id>
-----------------------------

  - 展示头像、昵称、简介、背景图和背景音乐
  - 展示该用户发布的所有公开博文
  - 登录访客可以留言
  - 背景音乐只在用户主动播放后播放，不强制自动播放

6. 个人设置 /settings/profile
-----------------------------

  修改昵称、简介、头像、主页背景图和主页背景音乐。上传资源统一进入媒体模块并进行安全校验。

7. 账号设置 /settings/account
-----------------------------

  修改登录账号和密码。修改账号时验证当前密码；账号保持全局唯一。

8. 后台 /admin
--------------

  仅管理员可进入。后台与普通用户的个人设置不是同一个概念，也不能依靠前端隐藏按钮实现权限控制。


五、数据模型规划
================

说明：社区关系数据具有唯一约束、关联查询和并发写入需求，TinyDB 不适合作为正式社区数据层。阶段一应迁移到 SQLite，并通过 SQLAlchemy 建模。若课程环境暂时不能迁移，也必须保持相同的数据结构和约束语义，并封装数据访问层，禁止继续维护嵌套分页快照。

1. users 用户表
---------------

  id              主键
  username        唯一登录账号，建立唯一索引
  password_hash   密码哈希
  role            user / admin
  status          active / banned
  created_at      注册时间
  last_login_at   最后登录时间

2. profiles 用户资料表
---------------------

  user_id          主键、外键 users.id
  nickname         公开昵称
  avatar           头像媒体路径
  bio              个人简介
  background_image 主页背景图路径
  background_music 主页背景音乐路径
  updated_at        更新时间

3. posts 博文表
---------------

  id          主键，所有详情、互动和管理操作均使用该 ID
  author_id   外键 users.id
  title       标题
  content     正文
  status      published / hidden / deleted
  created_at  发布时间
  updated_at  更新时间

禁止继续用 timestamp 作为帖子唯一标识；同一秒发帖会产生冲突。

兼容说明：数据库中的 legacy board 字段暂时保留以兼容既有 SQLite 文件，但所有旧值已迁移为 public，业务表单、页面和查询不再使用板块概念；后续正式结构迁移时可删除该兼容字段。

4. post_images 博文图片表
------------------------

  id          主键
  post_id     外键 posts.id
  file_path   图片路径
  sort_order  展示顺序

5. tags 与 post_tags
--------------------

  tags：id, name（唯一）
  post_tags：post_id, tag_id（联合唯一）

6. post_likes 点赞表
-------------------

  user_id     点赞用户
  post_id     被点赞帖子
  created_at  点赞时间

约束：user_id + post_id 联合唯一。点赞数由记录聚合，禁止只修改 posts.likes 整数或只写 localStorage。

7. comments 评论表
------------------

  id          主键
  post_id     外键 posts.id
  author_id   评论用户
  content     评论内容
  status      visible / hidden / deleted
  created_at  评论时间

评论昵称从 profiles 动态读取，不接收用户随意填写的昵称。

8. guestbook_messages 主页留言表
--------------------------------

  id               主键
  profile_user_id  被留言主页的用户
  author_id         留言者
  content           留言内容
  status            visible / hidden / deleted
  created_at        留言时间

9. media 媒体表
---------------

  id          主键
  uploader_id 上传用户
  media_type  image / audio
  file_path   存储路径
  mime_type   服务端检测的 MIME 类型
  file_size   文件大小
  created_at  上传时间

10. site_settings 平台设置表
-----------------------------

  key         唯一配置键
  value       配置值
  updated_by  管理员 ID
  updated_at  更新时间

11. admin_logs 管理日志表
-------------------------

  id, admin_id, action, target_type, target_id, detail, created_at

12. 废弃结构
------------

  - pagination 表：废弃。分页应直接查询 posts 并使用 limit/offset，不保存帖子副本。
  - admin.author_name：废弃。公开昵称统一来自 profiles.nickname。
  - entries.timestamp 路由标识：迁移为 posts.id。
  - comments.nickname：废弃，改为 comments.author_id。

七、团队任务分配
================

建议团队：3 人；如果只有 2 人，开发者 C 的任务由 A、B 按后端/前端拆分承担。

【项目经理 / 技术负责人】

  负责：需求边界、模型评审、接口约定、任务排期、代码合并、验收
  关键工作：
  - 冻结数据模型和权限矩阵
  - 每阶段开始前拆分任务，结束后按验收标准检查
  - 控制需求变更，确保先完成社区主链路

十、验收标准
============

1. 社区内容验收
---------------

  ☐ Alice 和 Bob 分别发帖后，两人的帖子都出现在社区首页
  ☐ Alice 可以在统一社区首页看到 Bob 的帖子
  ☐ 游客可以浏览公开帖子和用户主页
  ☐ 首页、标签页、个人主页的查询范围符合各自定义

2. 权限验收
-----------

  ☐ Alice 不能编辑或删除 Bob 的帖子
  ☐ Bob 可以编辑和删除自己的帖子
  ☐ 未登录用户不能发帖、点赞、评论或留言
  ☐ 普通用户不能访问后台接口
  ☐ 被封禁用户不能继续发布和互动

3. 发帖与内容展示验收
---------------------

  ☐ 博文支持标题、正文、标签和多张图片
  ☐ 发帖页不要求选择板块，所有公开帖子进入同一社区内容流
  ☐ 不同兴趣内容可通过标签聚合和发现
  ☐ 横图、竖图和大尺寸图片均保持比例并适应卡片及详情区域
  ☐ 非法文件类型、超大文件和伪造 MIME 文件被拒绝

4. 互动验收
-----------

  ☐ 每个用户对同一帖子最多保留一条点赞记录
  ☐ 刷新页面后点赞状态和数量保持正确
  ☐ 评论自动关联当前登录用户，不能伪造昵称
  ☐ 点赞和评论均能从帖子追溯到真实用户

5. 个人主页验收
---------------

  ☐ 点击帖子作者可进入其个人主页
  ☐ 主页显示指定用户的资料和公开博文
  ☐ 用户只能修改自己的头像、简介、背景图和背景音乐
  ☐ 个人主页首屏包含清晰的个人名片、统计信息和音乐入口
  ☐ 播放器支持进度、音量、切歌，并在普通页面导航后恢复当前歌曲与时间
  ☐ 进入他人主页不会未经确认强制替换当前正在播放的音乐
  ☐ 手机端播放器不遮挡导航、发帖按钮和正文
  ☐ 登录访客可以留言，主页所有者可以管理留言

6. 后台与系统设置验收
---------------------

  ☐ 管理员可以封禁用户、下架帖子和删除违规互动
  ☐ 平台名称、简介和公告由系统设置统一管理
  ☐ 所有重要后台操作写入管理日志

7. 数据与质量验收
-----------------

  ☐ 原有用户、帖子和评论迁移后不丢失
  ☐ 不再使用 timestamp 作为帖子唯一主键
  ☐ 不再使用 pagination 表保存帖子副本
  ☐ 核心社区链路自动化测试通过
  ☐ Python 编译、测试和手工演示均无阻断错误


十一、风险与应对
================

R1  当前实现方向错误
    风险：现有查询按 session.user_id 过滤，导致用户互不可见。
    应对：阶段一优先改为公开查询；只有编辑、删除和个人设置使用本人权限校验。

R2  TinyDB 并发和关联能力不足
    风险：点赞、评论和多用户同时写入时容易出现一致性问题。
    应对：核心功能前迁移 SQLite + SQLAlchemy；迁移前备份 db.json 并做记录数核对。

R3  点赞模型不真实
    风险：当前 likes 整数与 localStorage 无法确认是谁点赞，也容易被重复请求污染。
    应对：建立 post_likes 联合唯一关系，以服务端数据为准。

R4  timestamp 冲突
    风险：两个用户可能在同一秒产生相同时间戳，详情和互动无法可靠定位。
    应对：统一使用数据库 post_id；时间仅用于展示和排序。

R5  文件上传安全
    风险：路径遍历、伪造扩展名、超大文件、恶意媒体。
    应对：UUID 文件名、MIME 检测、大小限制、类型白名单、非执行目录和失败清理。

R6  音频自动播放限制
    风险：现代浏览器通常禁止未交互自动播放。
    应对：主页显示明确播放按钮，用户交互后播放并保存音量偏好。

R7  范围失控
    风险：推荐、关注、私信等功能挤占社区主链路工期。
    应对：严格遵守本期范围；M6 完成前不启动暂缓功能。

R8  第三方音乐接口不稳定与版权限制
    风险：参考项目通过网易云公开接口获取歌曲信息和播放地址，可能受接口变更、版权、跨域或限流影响。
    应对：本项目核心音乐能力以用户自行上传且有权使用的音频为准；第三方歌曲 ID 只作为后续可选增强，不能成为主页正常工作的依赖。

R9  动态背景与特效影响移动端性能
    风险：背景轮播、模糊、粒子、歌词动画同时运行会造成耗电、掉帧和文字可读性下降。
    应对：移动端关闭高负载粒子和弹幕，只保留静态/低频背景；支持减少动态效果设置，并以正文可读性优先。


十二、完成定义（Definition of Done）
====================================

一个任务只有同时满足以下条件才能标记完成：

  1. 功能符合本规划和权限矩阵，不以“页面能打开”代替业务完成。
  2. 服务端具备输入校验和权限校验。
  3. 核心逻辑有自动化测试，相关旧测试已同步更新。
  4. 页面有中文成功提示、错误提示和空状态。
  5. 不破坏旧数据；若修改模型，已提供迁移脚本和回滚说明。
  6. 代码通过编译和测试，且已由另一名成员完成评审。
  7. 验收人员能够按对应验收条目复现结果。


十三、项目经理结论
==================

阶段一和阶段二已完成社区数据模型、公开内容流和安全图片上传。下一步的优先级是先完成真实互动闭环，再建设具有个人氛围但不破坏社区一致性的主页与音乐体验：

  “所有人可以发现公开内容，作者控制自己的内容，管理员治理平台内容。”

后续所有页面、接口和测试都应围绕这条主线展开。视觉效果服务于内容发现和个人表达，不能以动画数量代替可用性，也不能让某个用户的主页音乐未经确认打断访客当前播放。


十四、UI 与音乐专项规划（参考 XHBlogs）
=======================================

1. 参考边界
-----------

参考项目采用 Next.js、React、Tailwind 和 Framer Motion；本项目不迁移这些框架，继续使用 Python Flask、Jinja2、Bootstrap、CSS 与原生 JavaScript。

参考项目采用 CC BY-NC 4.0 许可证。本项目只学习布局、交互思想和状态设计，不复制其图片、音乐、图标组合、组件源码、品牌文字或专属视觉素材。

2. 值得吸收的设计语言
---------------------

  - 半透明毛玻璃卡片：统一圆角、边框、模糊、阴影，而不是每页随意设置
  - 背景图片 + 柔和遮罩 + 主题色光晕，保证正文始终可读
  - 固定顶部导航：滚动时可收起，移动端改为简洁抽屉菜单
  - 个人名片：头像、昵称、简介、文章数、获赞数、评论数形成主页视觉核心
  - 内容卡片：封面、标题、摘要、作者、时间、标签和互动数层级明确
  - 音乐卡片：旋转封面、曲名、作者、进度和控制按钮形成可识别模块
  - 浮动播放器：离开个人主页后仍可继续控制当前音乐
  - 明暗主题持久化：localStorage 保存主题，避免页面切换后重置
  - 动效分级：桌面端可显示轻量粒子/光晕，手机端主动降级

3. 不应直接照搬的部分
---------------------

  - 不照搬个人博客首页的多入口功能宫格；社区首页仍以发现博文为主
  - 不加入 AI 猫、计算器、弹幕、天气等与当前核心需求无关的组件
  - 不使用复杂旋转式手机导航，优先保证发布、消息、主页入口容易找到
  - 不依赖网易云非正式播放地址作为核心音乐来源
  - 不默认自动播放，不让动画、歌词或背景抢夺正文注意力

4. 页面级 UI 规划
-----------------

  社区首页：
  - 顶部毛玻璃导航 + 居中搜索框 + 发布按钮
  - 主体保持响应式博文卡片流
  - 热门标签作为轻量发现入口，不拆分兴趣板块
  - 音乐播放器只显示紧凑悬浮控制，不占据首页主视觉

  用户个人主页：
  - 背景层：用户背景图、暗色遮罩、主题光晕
  - 第一行：个人名片占较大区域，音乐卡片占较小区域
  - 第二行：当前音乐状态/可选歌词栏；没有音乐时显示友好空状态
  - 第三行：该用户公开博文卡片
  - 页面底部：访客留言板

  博文详情：
  - 内容卡片保持较高不透明度，避免背景影响阅读
  - 图片继续使用响应式 contain 画廊和灯箱
  - 作者名片做成轻量入口，不在正文旁堆叠复杂挂件

  设置与后台：
  - 参考其左侧分类导航 + 右侧表单面板
  - 个人资料、视觉背景、音乐、账号安全分为独立标签页
  - 每次上传都提供预览、保存状态和失败原因，不采用“修改后看不出是否生效”的流程

5. Flask 下的音乐架构
--------------------

  服务端：
  - Media 继续保存文件路径、MIME、大小和上传者
  - 新增 user_music_tracks，关联用户、音频 Media、封面 Media、曲名、作者、排序和启用状态
  - 路由：GET /api/user/<id>/music 获取公开歌单
  - 路由：POST /settings/music 上传、排序、启用或删除自己的曲目
  - 服务端校验扩展名、实际 MIME、10MB 限制和资源所有权

  前端：
  - base.html 只保留一个全局 audio 元素，禁止每张卡片各自创建播放器
  - music-player.js 维护 playlist、index、playing、currentTime、volume、mode
  - localStorage 保存音量、曲目和播放模式；sessionStorage 保存当前时间
  - 普通 Flask 页面刷新后恢复曲目与时间，但必须由用户手势恢复播放
  - 进入用户主页时显示“播放 TA 的主页音乐”，由访客确认后切换歌单
  - 桌面端使用浮动胶囊播放器，手机端使用底部紧凑栏

  歌词：
  - MVP 不强制要求歌词
  - 后续可允许用户上传 UTF-8 LRC 文件并在浏览器解析时间标签
  - 歌词解析失败不能影响音乐播放，歌词文本必须限制长度并转义输出

6. 视觉令牌与组件复用
---------------------

在 custom.css 中集中定义 CSS 变量：

  --surface-glass-light / --surface-glass-dark
  --border-glass
  --shadow-card
  --radius-card
  --accent-primary / --accent-secondary
  --text-primary / --text-muted

统一复用以下 Jinja 片段：

  _navbar.html
  _post_card.html
  _profile_card.html
  _music_player.html
  _empty_state.html
  _pagination.html

避免复制多份点赞脚本、播放器脚本和卡片样式。

7. 性能与可访问性预算
---------------------

  - 首屏背景图片压缩为 WebP，建议不超过 500KB
  - 头像和封面设置明确尺寸并启用 loading=lazy
  - 同一时刻最多运行一种背景粒子效果
  - 手机端禁用粒子、弹幕和大面积 blur 动画
  - prefers-reduced-motion 下关闭背景轮播、旋转唱片和波形动画
  - 所有播放按钮具有 aria-label，键盘可操作，颜色对比满足正文阅读
  - 页面在 360px、768px、1366px 三个宽度进行人工验收
